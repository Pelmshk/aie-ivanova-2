Проект представляет собой REST API сервис для поиска кулинарных рецептов на основе списка ингредиентов, указанных пользователем. Система включает пайплайн предобработки данных, обучение модели, упаковку в Docker и инструменты наблюдаемости (метрики и health-check), а для поиска используется алгоритм BM25.

## 2. Постановка задачи и контекст

1. **Предметная область и задача:**
   - Задача относится к области Information Retrieval и рекомендательных систем;
   - Потенциальный пользователь хочет найти рецепты блюд, которые он может приготовить из имеющихся у него продуктов, введя их список, так, чтобы понадобилось докупить наименьшее количество дополнительных ингредиентов.

2. **Формулировка задачи в терминах ML/ИИ:**
   - Входные данные: набор текстовых строк (названия ингредиентов);
   - Целевая переменная: релевантность рецепта запросу;
   - Выход: упорядоченный по совпадению с запрошенным списком список релевантных рецептов с оценками схожести.;
   - Требования к модели: быстрый отклик, высокая точность ранжирования по релевантности.

3. **Целевые метрики качества:**
   - Для оценки модели используются метрики:
     - NDCG@10 (Normalized Discounted Cumulative Gain) - оценка качества порядка выдачи (релевантный рецепт должен быть наверху);
     - MRR (Mean Reciprocal Rank) - насколько высоко находится первый релевантный результат;
     - Recall@K / Precision@K - доля найденных релевантных рецептов среди топ-K.

## 4. Модели и подходы

В ходе работы были опробованы три подхода к поиску (эксперименты в notebooks/02_baseline_models_training.ipynb и 03_advanced_models.ipynb)

1. **Базовые (baseline) модели:**
   - В качестве baseline-модели использовался классический подход для текстового поиска TF-IDF и Cosine Similarity

2. **Улучшенные модели и эксперименты:**
   - В качестве улучшенной модели используется вероятностная модель ранжирования Okapi BM25;
   - В отличии от использованной baseline-модели, она учитывает насыщение частотности терминов и длину документа.

3. **Нейросетевые модели (если применимо):**
   - Использовалась предобученная модель all-MiniLM-L6-v2 для создания векторных эмбеддингов.
   - Модель позволяет искать по контексту, а не только по точному совпадению слов.
   - Модель не была выбрана, поскольку показала схожие результаты метрик с более простыми вариантми, однако требовала гораздо больше времени на обучение.

Здесь важно показать, что выбор финальной модели был осмысленным.

1. **Экспериментальный протокол:**
   - Данные разделены на обучающую (80%) и валидационную (20%) выборки по запросам;
   - Для каждого рецепта был индексирован объединенный текст；
   - Метрики рассчитываются на валидационной выборке.

2. **Сравнение моделей по метрикам:**

   Пример таблицы (адаптируйте под свои метрики):

   | Модель / конфигурация   | Описание                             | NDCG@10   | MRR     | Recall@10 | Скорость обучения   | Комментарий              |
   |-------------------------|--------------------------------------|-----------|---------|-----------|---------  |--------------------------|
   | TF-IDF                  | Векторизация TF-IDF и косинусное сходство  | 0.934     | 0.918   | 0.983     | 0.03      | Хороший baseline, работает быстро.  |

   - эмбеддинги оказались менее эффективны, так как поиск по ингредиентам является преимущественно лексической задачей, а не семантической.

## 6. Архитектура решения и сервис

Опишите, как из модели получился работающий сервис:

1. **Архитектура пайплайна:**
   - Jupyter Notebook обрабатывает сырой CSV, чистит поле содержащее список ингредиентов, обучает модель BM25 и сохраняет её в artifacts/models/bm25.pkl.
   - FastAPI приложение загружает сохраненную модель и обработанные данные (recipes_processed.parquet) в память;
   - При запросе /search текст пользователя нормализуется, проходит через модель BM25, после чего возвращаются топ-N рецептов.

2. **API и endpoints:**
   - GET / - возвращает список эндпоинтов в приложении
   - POST /search, POST /search - принимает список ингредиентов, возвращает ранжированные рецепты;
   - GET /health - возвращает статус сервиса и загрузки модели;
   - GET /metrics - возвращает базовые метрики.

3. **Технологический стек:**
   - Backend: Python 3.10+, FastAPI, Uvicorn;
   - ML: rank-bm25, scikit-learn, pandas;
   - Deployment: Docker. Чтобы собрать и поднять образ Docker, используются команды:
     
```bash
cd project
docker build -t recipe-recommender:v2 .
docker run -p 8000:8000 recipe-recommender:v2
```

## 7. Наблюдаемость, конфигурация и безопасность

Кратко опишите:

1. **Логи и наблюдаемость:**
   - Реализован ObservabilityMiddleware, который логирует каждый запрос (метод, путь, время выполнения, статус-код);
   - Доступен endpoint /metrics для мониторинга количества успешныхи ошибочных запросов, а также среднего времени ответа;
   - Логи пишутся в консоль и в файл project/logs/api.log.

2. **Конфигурации:**
   - В `configs/`, `.env.example` вынесены все настройки длч возможности их изменения без изменения самого кода:
     - HOST - адрес привязки сервиса (по умолчанию 0.0.0.0 для доступа извне),
     - PORT - порт, на котором поднимается API (по умолчанию 8000),
     - LOG_LEVEL - уровень детализации логов (INFO, DEBUG, WARNING, ERROR),
     - MODEL_PATH - путь к файлу обученной модели,
     - DATA_PATH - путь к обработанному датасету с рецептами,
     - DEFAULT_TOP_K - количество рецептов, возвращаемых по умолчанию (например, 10),
     - MAX_TOP_K - лимит на максимальное число результатов в одном запросе.
     - MIN_SCORE_THRESHOLD - минимальный порог релевантности запросу.

3. **Безопасность:**
   - Секреты и переменные окружения не хранятся в репозитории (используется .env.example и .gitignore);
   - Используется валидация данных через Pydantic для защиты от некорректных входных данных;
   - В репозитории отсутсвуют чувствительные данные.

## 8. Ограничения и дальнейшая работа

Текущие ограничения:
- Лексическая зависимость - модель ищет точное совпадение слов;
- Отсутствие ранжирования по качеству - рецепты сортируются только по текстовой релевантности, без учета их рейтинга или популярности;
- Упрощенная нормализация - регулярные выражения могут некорректно обрабатывать сложные составные ингредиенты.
Можно добавить:
- Гибридный поиск (комбинация BM25 и семантического поиска);
- Учучшенное ранжирование с учетом рейтинга и времени готовки при расчете финального скора;
- Внедрение пользовательских профилей и истории предпочтений;
- Переход от Parquet и JSON файлов к базе данных для хранения рецептов.
